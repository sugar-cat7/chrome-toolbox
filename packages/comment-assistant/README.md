# comment-assistant (コメントアシスタント)

Chrome MV3 extension that translates live chat and video comments into Japanese, classifies them and judges abuse with a local llama.cpp server. It changes only how comments are shown: nothing is deleted or moderated. Design: spec §7 in the [design spec](../../docs/superpowers/specs/2026-10-28-chrome-ai-extensions-design.md); tasks: [comment-assistant plan](../../docs/superpowers/plans/2026-10-28-comment-assistant.md).

## Status

Implemented in the background service worker:

- Message routes (`src/protocol.ts`): `llm/status` (connection check), `comments/ingest` (comments read from a page; `process: false` for comments only to be stored, `left` when the page's chat leaves the viewer, a comment marked `held` while its line waits for its judgement; the reply carries `lastError` while the latest model batch failed), `comments/context` (a page's stream: partition, streamer, title), `comments/stats` (counters per channel and the median first-annotation latency), `comments/stream` (the stream a tab shows), `comments/hidden` (the channel's hidden comments for review), `comments/feedback` (the viewer's verdict on one of them), `comments/export` (every saved verdict as JSONL), `comments/feedback/clear` (forget every verdict) and `comments/summary` (the channel's chat summary over the last 5, 15 or 30 minutes). `comments/stream`, `comments/summary` and the four hidden-comment and feedback routes answer extension pages only (the sender's URL starts with this extension's base URL and its origin is not opaque, also when the side panel is opened as a tab); a content script gets `sender_forbidden`.
- Stream context (`src/stream-context.ts`): the service worker keeps what pages reported about the 16 most recent streams. The live chat frame knows only its video id; the watch page names the streamer (the owner link's `@handle`, or the channel id for `/channel/<id>`) and the title once YouTube has filled in its metadata for that video, and Twitch names its channel login and the stream title once its stream information section links to that channel. Each report is passed to every frame of the tab, so the chat frame learns its streamer; a frame that sends comments without the streamer the service worker knows (a popout opened before its watch page) is told once. The side panel asks for a tab's stream; the service worker then asks that tab's top frame which partition it shows, so a tab that navigated away shows none. Ingest messages and ping answers carry the frame's streamer and title, so a restarted service worker learns them again.
- Per streamer: the filter settings, the feedback (allowlist, corrections, raised threshold) and the text cache are keyed by the streamer, or by the stream (video id, Twitch login) while the streamer is unknown (a popout without its watch page). Per stream: the spoiler targets (`chrome.storage.local` key `spoilerNotes`, the newest 100 streams), so a streamer's next stream starts without them. Comment stores, stats and hidden lists stay per partition (`<videoId>`, `<videoId>#comments`, login).
- Comment pipeline (`src/pipeline.ts`, `src/fastpath.ts`), per comment and in this order:
  1. Text without letters or digits (emoji, stamps, empty Super Chats) is skipped and stays in the original.
  2. Stock reactions (`lol`, `www`, `草`, `gg`, `888`, `kekw` and similar, alone, repeated, stretched like `LMAOOO` or spelt as an emote like `LUL` and `PogU`), comments made only of widely used Twitch, BTTV, FFZ and 7TV emotes and laughter (`KEKW`, `catJAM`, `hahaha`) and digit-only comments become `chatter` by rule, without the model or Clef. Reactions that all read the same keep their short translation (`lol` and `LUL` → （笑）); the rest stay untranslated. An @mention is a name, never a reaction.
  3. Copypasta (one phrase of at least 6 characters repeated 3 or more times in a row, 20 or more characters in all; laughter never counts) is `spam` by rule, without the model or Clef, and listed as a rule verdict. A viewer's copypasta with an abuse cue (step 8) instead goes to the model and Clef with a batch: Clef's score at or above the threshold makes it `abusive`, a lower score or a failed Clef request keeps the rule's `spam` (R53), and so does expiring or being dropped while it waits (R55).
  4. A comment whose normalized text the model answered before for the same streamer, stream context (title, spoiler targets), genre and stream categories (R62) and the streamer's latest corrections (R53) reuses that answer (2,000-entry text cache): a new correction makes the model answer again.
  5. The rest goes to the model. With no batch running, a comment is sent at once; while one runs, new comments of the same channel wait up to 500 ms and are sent up to 3 at a time. Comments whose lines a chat keeps out of sight until judged (marked `held` by the content script, R52) go first while they can still be judged before their lines come in, oldest first, the order the chat lets them in. That window is 2,000 ms of the hold, less 250 ms of the content script's flush, less the 90th percentile (nearest rank) of the durations of the latest 20 model batches that got a reply (from a batch's start to its reply, Clef included), within 0 to 1,750 ms; not the median, which lost to newest first when batch times vary (R59). Until a batch has been measured, a batch is taken to last 450 ms, which gives 1,300 ms (R58). Every other comment, a held one past that window included, goes newest first (R57). The first comment in that order decides the batch's channel. Lines on screen when a chat comes back are never held (R44). A plain oldest-first order (R56) spent the model on lines that would come in unjudged anyway and fell behind for good near capacity.
  6. The language is guessed from the script. Japanese comments are classified but not translated; kanji-only text counts as Japanese when it has full-width `ｗ`, `！` or `？`, a mark such as `々` or `〜`, or ends a short text with `w`. Any other comment of kanji, digits and symbols only, without a character or word only Chinese uses, is Japanese when at least half of the latest 200 comments of its channel sent to the model were detected as Japanese (R60); the channel counts the detected languages, never the ones this rule gave.
  7. One chat request per batch translates and classifies every comment into `abusive`, `spam`, `question`, `important` or `chatter`, or one of the stream categories the stream has on (`spoiler` and the genre categories, see below; R62). The reply is one short line per comment, constrained by a GBNF grammar; a broken line fails only its own comment, and `max_tokens` leaves every line room to reach its grammar bound. A translation that reaches that bound is kept once when it repeats one piece (a chant, R42) and otherwise dropped: the comment keeps its category untranslated, cached like any answer (R46). The prompt asks for the translation alone, the grammar allows no `<` or `>`, and a closing parenthetical that repeats the original or the translation before it, or holds a note, is removed, and so is a kana reading right after a kanji word of the original (`神風 (かみかぜ)` → `神風`, R60). The stream title, the stream's spoiler targets (typed in the side panel) and the streamer's latest corrections go into the batch's user turn, after the fixed system turn, so llama.cpp's prompt cache keeps working; names from the title are kept as written.
  8. Clef (`POST /v1/systemone`, one request per comment on its own queue) judges abuse only where it matters (R43): a comment with an abuse cue (a self-written list of Japanese, English and Spanish insults, calls for death or violence, sexual insults and slurs; Japanese anywhere in the text, English and Spanish as whole words, outside @mentions; a stream format named after an insult, such as `馬鹿凸`, is none, R60) goes to Clef while the model runs, and a comment without one that the model calls `abusive` goes to Clef after the reply; the batch is shown once Clef answered. A post by the streamer, a moderator or a verified account and a text the viewer marked fine for the streamer never go to Clef (R53). Every other comment keeps the model's category without Clef (`clefSkipped` counts them). Where Clef answered, a score of 0.8 or more makes the comment `abusive` (a channel's feedback can raise this, see below) and a lower score overrides an `abusive` category from the model. A failed Clef request never fails the batch or stops its chat call (R53), and when the call while the model runs found Clef unreachable or silent, the comments the model called `abusive` are not asked after the reply, so a batch never waits for two timeouts (R55): its comments keep the model's category and `judgeError` names the cause (`network_failed` when the request was rejected or timed out, `response_invalid` for an HTTP error of that request, such as a 503 while the model loads). HTTP 501, 404 or a router's 400 "model '<name>' not found" (`clef_unavailable`) means Clef is not there: the model's category judges abuse from then on, until the settings change. A reply that needed Clef but got no score is not reused from the text cache, unless its text is allowlisted (every copy under the same scope is too).
  9. The category a comment shows with, from the model's verdict: a post by the streamer, a moderator or a verified account (R38) is never `abusive`, `spam` or a stream category: a link or the model's `spam` makes it `important`, copypasta without a link and the model's `abusive` or any stream category (`spoiler`, `instruction`, `relay`, `ghosting`, `privacy`, `sensitive`) make it `chatter` (R53, R62). For everyone else, a stream category stands only when the stream has it on, else it is `chatter` (R31, R62: the grammar already allows only those codes); the model's `spam` stands only on a comment with a link (`http://`, `https://` or `www.`), else it is `chatter`, while copypasta stays `spam` by rule (R60); a `question` on a comment mostly in Latin script needs a question mark or a question word (`what`, `do`, `cómo` …) within its first three words after any @mentions, vocatives (`chat`, `guys`, `bro`) and emote names, and is never one interjection (`what`, `huh`, `um`, `uh`, `eh`, `wtf`, `omg`, `bruh`, `wait`, in any case and stretched) with only `?` or `!` after it, else it is `chatter` (R38, R40, R60); Clef decides abuse as in step 8; and a text the viewer marked fine for the streamer is `chatter`.
  10. A comment that waited more than 8 s without reaching the model is shown in the original (`expired`); copypasta keeps its rule verdict (R55), and another one that ends in a question mark is then a `question` by rule, still untranslated (R38), unless it is one interjection (R60). Beyond 200 waiting comments the oldest are dropped (`dropped`) and shown in the original, copypasta with its rule verdict.
  11. The results go back to the frames that sent the comment for processing as a `comments/annotations` message.
- Genre categories (R62, `streamCategories` in extension-core, `src/stream-context.ts`): besides the categories every stream has, a stream has its own on or off, by its genre, its own rules and the viewer's spoiler note. The prompt's fixed system turn defines only `a` abusive, `s` spam, `q` question, `i` important and `c` chatter, and tells the model to use a stream category only as the user turn defines it. The user turn names the genre (`Stream genre: fps (…)`) and defines, one line each, only the stream categories that are on; the grammar allows only their codes besides the base ones. Codes and side panel labels:

  | Category      | Code | Label          | On in                                                                                        | Default |
  | ------------- | ---- | -------------- | -------------------------------------------------------------------------------------------- | ------- |
  | `spoiler`     | `p`  | ネタバレ       | story, horror, puzzle_rta, watchalong, sports_viewing; any stream with spoiler targets (R31) | 伏せる  |
  | `instruction` | `n`  | 指示           | fps, story, horror, puzzle_rta, board                                                        | 消す    |
  | `relay`       | `r`  | 他配信の話題   | every stream                                                                                 | 消す    |
  | `ghosting`    | `g`  | ゴースティング | fps, board, deduction                                                                        | 消す    |
  | `privacy`     | `v`  | プライバシー   | every stream                                                                                 | 消す    |
  | `sensitive`   | `e`  | センシティブ   | every stream                                                                                 | 消す    |

  Genres: `fps` (FPS, battle royale, PvP, fighting), `story` (story, RPG, adventure), `horror`, `puzzle_rta`, `chat` (雑談), `singing` (歌枠), `watchalong` (同時視聴), `sports_viewing` (観戦, watch parties), `board` (mahjong, board and card games), `deduction` (人狼, Among Us) and `other` (unknown). A stream's genre is given to the stream context (`classify`, with its relaxations); until Task G2 detects it every stream is `other`. Relaxations turn a category off for one stream: 参加型, アドバイス歓迎, 指示OK and "backseat me" turn `instruction` off; ネタバレあり, ネタバレOK, 2周目 and "spoilers ok" turn the genre's `spoiler` off, but never one the viewer asked for with spoiler targets. The title's own words relax its stream (`relaxationsIn`); bans and warnings (ネタバレ禁止, ネタバレ注意, 指示NG) and a game named after spoilers relax nothing. These categories are the model's alone: Clef still judges abuse only (R43). `pnpm bench:genre -- --server <url> --model <name>` runs the self-written sets in `packages/extension-core/test/fixtures/genre-eval/` with this prompt and grammar and reports per-category precision and recall and the share of chatter flagged; the results are in [adoption](../../docs/adoption.md).

- Only the chat in front of the viewer is processed (R44, R49). Comments a frame sends with `process: false` (its chat is not in front, or they are off screen; see the content script) are stored as they are, state `stored`: no model, no Clef, no rule or cache answer and no annotation, so the chat shows them unmarked; nothing else is touched. When a frame's chat leaves the viewer it says so (`left`, a message of its own): the channel's comments still waiting for the model (in the batch window or the backlog) that no other frame shows are stored at once, while a frame still in front keeps its comments; batches already with the model finish. A frame sending comments only to store them is not one they wait for (R50): it gets an answer that exists already, but its leaving keeps nothing from being stored when the frames showing them leave. A stored comment that a frame sends again with `process` (on screen when its chat came back) is processed then: its record waits for the model again (`pending`) and is completed in place; one still with the model is not asked again. `stored` in `comments/stats` counts the comments stored and not processed since (`records` is the channel's store size). Within one ingest message, as in the backlog, the newest comments go to the model first.
- Hidden comments and feedback (`src/feedback.ts`): comments that end up `abusive`, `spam` or a stream category (`spoiler`, `instruction`, `relay`, `ghosting`, `privacy`, `sensitive`) are listed per channel (the newest 200, in memory). The viewer's verdict on one, `ok` (fine) or `correct`, is saved in `chrome.storage.local` only (nothing is sent anywhere); the first verdict on a comment wins. `ok` shows the comment, and every other hidden copy of its text in the channel, again in every frame that got its annotation, also one that only stored it after it was answered (an annotation with `override: 'show'`; the latest four frames of each kind, R53) and, for that streamer (in every stream of theirs), makes the same text `chatter` from then on, puts the latest five such texts into the batch prompt (user turn, so the fixed system prompt stays cacheable) and, once three different restored abusive texts average a Clef score of 0.8 or more, raises the abuse threshold to 0.9 or their average, at most 0.95. A verdict takes effect at once; when storage cannot take it the answer says `persisted: false` and the next write saves it. If the saved verdicts cannot be read, comments are still processed with session-only verdicts and the store reads again later (at most three reads, 30 s apart). The export has text, translation, category, Clef score, verdict and time; no author or channel.
- Toolbar badge (`src/badge.ts`, R54): per tab, the number of the tab's stream's hidden entries without a verdict: comments classified abusive, spam, spoiler or a genre category, whether the filters removed, concealed or only listed them for review (its live chat and video comments together; empty at 0). It is set with `chrome.action.setBadgeText` only when it changes: when the pipeline lists a comment, a verdict is given, the feedback is cleared, a channel is dropped, the tab's top frame reports another stream or none, or a badged tab finishes loading a page (`tabs.onUpdated` `complete`: its top frame is asked with `comments/ping`, and no answer or `{}` empties the badge; Chrome keeps a tab's badge across navigations). After a service worker restart a tab is asked only when Chrome still shows a badge on it (`action.getBadgeText`). No polling and no extra permission.
- Retention: the reviewed texts (with their translation, category, Clef score, verdict and time) stay on this device until newer verdicts replace them (the newest 1,000 are kept) or the viewer clears them with `comments/feedback/clear`, which also drops every allowlist and raised threshold.
- Bounds: a comment that waited more than 8 s without reaching the model is shown in the original (`expired`); at most 200 comments wait, newest first; each channel keeps at most 30 minutes or 5,000 comments; a request times out after 30 s. At most 4 channels are kept: a new one takes the place of the least recently processed channel (R53). Comments only to be stored never evict a channel with comments waiting for or with the model, nor one processed in the last minute; of channels never processed, the one that sent comments longest ago goes first (R55). Without room they are not stored and count as `unstored` for their channel (R55). An evicted channel's records, hidden list and summaries go.
- Slots: one batch at a time on llama-server slot 1 (slot 0 is for subtitles). When `GET /props?model=` reports three or more slots, extra batches use the spare slots, up to 4. A pipeline built while llama.cpp did not answer `/props` asks once more after its first answered chat (R53). A summary takes a comment slot of its own between batches: while it runs, batches use the other comment slots (none on a 2-slot server, so comments wait or expire). When every slot is busy it waits: a slot freed by a batch goes to the waiting summary before the batches that queued meanwhile, and a slot freed by a summary goes to the waiting batches first, so summaries never run back to back ahead of them (R36). One summary per channel waits at a time: a newer request of the channel, of any window, takes its place, and the replaced one is answered with its counted parts without the model.
- Summaries (`src/summary.ts`, decision R32): one llama-server slot holds 4,096 tokens, so the model gets only what it must judge and everything countable is counted from the stored comments of the window: how many, in which languages (most first), the oldest one's time (later than the window start when the 5,000-comment store limit cut it short), the three busiest minutes (abusive comments and spam left out) and the five newest important comments (each text once). Stored comments (R44) count toward the total, the languages and the busiest minutes; `unprocessed` is how many of the window's comments were only stored. The comments are read again when the summary gets its slot, so it covers what arrived while it waited. The model reads at most 2,400 characters of lines: the comments the chat shows (not abusive, spam, spoiler or a genre category) that were answered or only stored, as the viewer reads them (the translation; Japanese and stored comments as written, a stored one as chat), the same normalized text once with its count, first the questions (the 40 most asked), then up to 8 texts of each busy minute, then the rest, most written first. Its reply (256 tokens, a GBNF grammar) gives up to 4 topics, up to 5 merged questions and a heading per busy minute; a merged question's count is the number of comments it stands for. If llama.cpp is down or answers outside the grammar, the counted parts come back without topics, with the questions unmerged and marked `modelFailed`; the model is not asked when there is nothing to read. Requests for the same channel and window share one run, and while the channel's comments are unchanged (a revision bumped by every stored comment, in-place update and verdict) and the window holds as many, the last summary is returned (the 8 most recent are kept, in memory only; one made without the model's answer is made again).
- The service worker keeps no timer for summaries: the side panel asks for each one (R35).
- A change to the saved settings rebuilds the pipeline with the new URL and model names. The rebuild clears the comment stores, hidden lists, summaries and the text cache, and Clef is tried again; the saved verdicts stay.
- Stats (`comments/stats`): per channel, the stored records, `stored`, `pending`, `dropped` (waiting comments given up: beyond 200 waiting, or the channel was evicted), `unstored` (comments only to be stored that found no room, R55), `failed`, `cached`, `trivial`, `expired`, `clefSkipped`, the judge in use and the latest errors, and `latencyP50Ms`: the median time from a comment's arrival to its first annotation over the channel's latest 200 comments that entered the model queue (a translation, a failed line, a cache answer after waiting, or the original after expiry or a drop; rule and immediate cache answers do not count, R55).

Implemented in the content script (`src/entrypoints/chat.content.ts`, every frame of `www.youtube.com` and `www.twitch.tv`; it does nothing on pages without comments):

- Pages: YouTube live chat (`/live_chat`, `/live_chat_replay`: the watch page's chat iframe and the popout), YouTube video comments (`/watch`, top-level comments) and Twitch chat (`www.twitch.tv`). Each site has an adapter in `src/sites/` with its selectors at the top. Comments are read from the DOM the page already shows; there are no requests to YouTube or Twitch.
- The channel (store partition) is the YouTube video id for its live chat and chat replay (the iframe takes it from the watch page that embeds it), `<videoId>#comments` for the same video's comments, and the Twitch channel login (Twitch's own pages such as `/directory` are not channels).
- Stream reports (`comments/context`): on start, after a navigation and when the page shows new metadata. On a watch page the session watches one attribute (`ytd-watch-flexy`'s `video-id`), which YouTube changes about a second after `yt-navigate-finish`, together with the title and owner link. Twitch's in-app moves between channels are followed through the Navigation API's `navigatesuccess` (Twitch has no event of its own); the channel left is sent as `left`, so its comments still waiting for the model are stored, not processed after the viewer moved on (R49). Until the page shows the channel's title (YouTube's `video-id`, Twitch's stream information linking to `/<login>`) the session watches that one element and reports the title once it appears, then stops watching; a later title change on Twitch is picked up with the next chat batch. Leaving a stream page (YouTube home, Twitch's directory) is reported too. The top frame answers the service worker's `comments/ping` with the partition it shows.
- Reading (`src/sites/observe.ts`): one childList observer on the chat container, plus shallow observers on its ancestors that move it to a new container when the site replaces the list (YouTube's Top chat / Live chat switch); while the container is missing, the site's app element (`yt-live-chat-app`, `ytd-comments`, Twitch's `#root`) is watched for it and checked at most once a second. Text is cut to 1,000 characters before it is sent.
- Only what is in front of the viewer is processed (R44, R49). The chat is in front while its page is visible (`document.visibilityState`: not a background tab or a minimized window, which hides the live chat iframe too), shown (no `pagehide`), has a viewport (an iframe resized to nothing reports only a `resize`) and its container intersects the viewport (an `IntersectionObserver`: a chat collapsed, closed or scrolled away does not). Seen live on 2026-10-30: YouTube's chat close button navigates the chat iframe to `about:blank` (its document goes away: `pagehide`) and hides `ytd-live-chat-frame`; Twitch's collapse keeps its message container in the page under an ancestor with `display: none`, which the observer reports. While in front, new lines are read and sent for processing in batches at most 250 ms apart. Otherwise they are kept and read when sent for storing only (`process: false`), at most once a second (a hidden tab may delay that further; a line read late is read whole). Leaving the viewer is sent at once as `left`; the lines waiting for their flush are stored. Coming back, and starting in front, the reader looks once at which lines are on screen: every one of them is sent for processing, in page order (the service worker takes the newest first), also one processed or stored before (the session shows one already answered as it is and the service worker asks the model about none twice, so lines stored when the chat left are processed now), and the rest is stored. Video comments are instead processed one thread at a time once it comes within one viewport height of the screen (`rootMargin: '100% 0px'`) while the page is in front, and never stored, so the reader never says it left (R50: threads already with the service worker are answered as usual); threads that came near just before the page was hidden stay watched and are looked at again on return; at most 1,000 threads are watched at once, and a thread that leaves the page is no longer watched.
- Display (`src/display.ts`): the message element gets `data-ca-category`, `data-ca-mode` (`show`, `highlight`, `blur` or `hide`) and `data-ca-label`; one injected `<style>` draws them. A removed comment (`hide`, shown as 消す) leaves the chat whole (`display:none` on the message element), with no label in its place, and cannot be revealed in the chat: the side panel's 非表示 tab lists it and "問題なし" puts it back (R54). A concealed one (`blur`, shown as 伏せる) is a bar of its category's colour labelled `伏せたコメント（<label>）· クリックで表示` in the bar's own opaque ink (black, or white on the spoiler colour; at least 4.5:1 contrast whatever the page's light or dark scheme; every category has a colour of its own: red, grey, purple, blue, orange, green, and for the genre categories teal, pink, indigo, brown and yellow), its text, images and badges hidden but its height kept (R51); a click reveals it. A translation goes into the comment's plain text (as text, never markup, marked `（訳）`); the text of links and mentions, and emoji, stay as they are, and the original comes back exactly when translations are turned off. Stopping takes the display off again (original text, no `data-ca-*` attributes), leaving any text the site has changed since.
- Judged before shown (R52, `src/hold.ts`): a line the page adds while the chat is in front gets `data-ca-wait` (`display:none`, so it takes no room; the site's own element, never a copy) as the page adds it, before it is read, and comes in once its annotation is written, in the same turn, so a concealed line is never seen as written. Lines come in in posting order: one answered early waits for every line before it, and every line that can come in does so in one pass. A line comes in as it is 2 s after the page added it (a later annotation still applies), a line holding no comment (a notice) at its read, and the oldest when more than 300 wait. Lines stored or looked at on return (R44) never wait. Leaving the viewer, a replaced list, another channel and stopping let every waiting line in. Nothing waits while the filters turn it off or while llama.cpp cannot be reached (the latest ingest reply carries `lastError: network_failed`, or the ingest itself failed); the lines waiting then come in at once. A batch answered badly (`response_invalid`) does not stop the wait. Deadlines are on `performance.now()`. Before letting lines in the hold reads the chat's scroller (the nearest ancestor of the list that scrolls) once: one at its end (within 8 px) is scrolled to its end again after; otherwise the line the viewer reads is kept where it was: the nearest line before the ones let in that is laid out and was not written in the same pass, read after the annotations are written (a late 消す may have just removed the line next to them). Seen live on 2026-11-02: YouTube's `#items` sits absolutely at the bottom of `#item-offset`, whose height YouTube sets itself, inside `#item-scroller`, so a line let in grows the list upwards without changing the scroll height: at the end it shows at once, and while the viewer reads above, the lines would move up by its height (the hold scrolls back by it). Twitch's lines are in the normal flow of `.scrollable-area`, which the hold scrolls to its end. Both sites stop adding lines while the viewer reads above.
- Filters per streamer (`src/filters.ts`) are read from `chrome.storage.local` key `filters:<site>:<streamer>` (the stream's video id or login while the streamer is unknown; the chat frame switches to the streamer's key once the service worker names it) and followed as they change; the defaults are abusive, spam and the genre categories (instruction, relay, ghosting, privacy, sensitive, R62) `hide` (消す: highlighting or concealing them still draws the eye, R54), spoiler `blur`, question and important `highlight`, chatter `show`, translations on, and new lines wait for their judgement (`holdUntilJudged`; settings saved before it existed wait too). A saved record carries `v: 2` (R56); the genre categories need no new version, since a record holds only the modes the viewer chose. Only a record without a version that lists all six pre-5d categories is read as saved before Task 5d, its entries equal to that panel's defaults acting as defaults again (R34). A comment the viewer marked as fine (`override: 'show'`) is shown whatever the filters say.

Implemented in the side panel (`src/entrypoints/sidepanel/`, `src/panel.ts`; mock B):

- The header names the active tab's stream (title and streamer). It is asked for when the panel opens and again when another tab is activated, the tab finishes loading or a page reports a stream change; there is no polling, and every listener is removed when the panel closes.
- 要約: the stream's chat over the last 5, 15 (default) or 30 minutes: main topics, frequent questions with their counts, the busiest minutes (time, a bar, the heading and the count) and important comments (author：text), with the number of comments and their languages, and "直近 N 分ぶん" when the store limit cut the window short. It is asked for when the tab opens, the window changes or "更新" is pressed; with "自動更新（2分ごと）" on (the default) the panel asks again every 2 minutes while it is visible, and at once when it comes back into view. The timer stops when the toggle is turned off, the panel is hidden or the tab is left. When the model could not summarize, the topics read "話題の要約に失敗しました（件数と盛り上がりは表示しています）". When some comments of the window were only stored because they were not on screen, it says "画面に出ていなかった N 件は未翻訳". A failed request keeps the last summary and says what went wrong.
- フィルター: per category show (表示), highlight (ハイライト), conceal (伏せる; stored as `blur`) or remove (消す; stored as `hide`); translations on or off; the original text; 判定してから表示する（最大 2 秒）(`holdUntilJudged`, on by default), saved at once for the streamer (the chat follows); and the spoiler targets (what you do not want spoiled, up to 300 characters), saved for this stream only, half a second after you stop typing, when you leave the field or when the panel closes.
- 非表示 (チャットから外したコメント): the comments of this stream classified as abusive, spam, spoiler or a genre category (指示, 他配信の話題, ゴースティング, プライバシー, センシティブ) and so taken out of the chat (chat and video comments), newest first, with the original, the translation, the reason, Clef's probability and the time. "問題なし" puts the comment back in the chat and keeps such text visible for the streamer; "正しい" confirms it. When a verdict could not be saved yet the panel says it will be saved later. "書き出す（JSONL）" saves every verdict as a file; "フィードバックを消去" forgets them after a confirmation, and the list then shows the confirmed comments as not judged yet.
- 設定: the llama.cpp connection, the model names sent to the router (translation, Clef), whether Clef or the translation model judges abuse, and the stream's processing counters (R53): 処理待ち (waiting for the model), 原文のまま（処理しきれず） (expired and dropped), 画面外で未処理 (only stored), 保存できず (`unstored`, shown only when there are some) and 応答の中央値 (`latencyP50Ms`). They are asked for when the tab opens and when "更新" is pressed; nothing polls.

## Use

1. Start `llama-server` with the `gemma4-e4b` and `clef-flash` models as described in [docs/llama-server.md](../../docs/llama-server.md).
2. Build: `pnpm --filter @chrome-toolbox/comment-assistant build` (from the repository root).
3. In `chrome://extensions`, turn on Developer mode, choose "Load unpacked" and select `packages/comment-assistant/dist/chrome-mv3`.
4. Click the toolbar icon to open the side panel. In "設定", enter the server URL (default `http://127.0.0.1:18083`) in "llama.cpp の接続先" and press "接続を確認".
5. Open a YouTube live stream (or a Twitch channel): chat lines come in once judged (at most 2 s later), translated, highlighted, concealed or removed. The side panel shows the stream; set its filters in "フィルター" and review hidden comments in "非表示".

Permissions: `storage` and `sidePanel`; host access to `localhost` and `127.0.0.1`. Any other server host is an optional permission that Chrome asks for when you check that URL. The content script runs on `www.youtube.com` (all pages, since YouTube reaches watch pages without a reload; it reads only live chat and watch pages) and on `www.twitch.tv`.

## Layout

| --------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `src/entrypoints/background.ts`   | Service worker entry; the toolbar action opens the side panel.                                          |
| `src/entrypoints/sidepanel/`      | Side panel (React): stream header and the summary, filter, hidden-comment and settings tabs.            |
| `src/panel.ts`                    | The side panel's port: active tab's stream, filters, review routes, settings; its listeners.            |
| `src/entrypoints/chat.content.ts` | Content script entry: the site adapters and the content script context's cleanup.                       |
| `src/chat.ts`                     | Picks the adapter by URL and restarts on YouTube navigation; the session: ingest, annotations, filters. |
| `src/sites/`                      | Site adapters (selectors, ids, channel) and the comment observer.                                       |
| `src/display.ts`                  | Display attributes, translations in place, injected style, filter defaults.                             |
| `src/badge.ts`                    | The toolbar badge: each tab's removed comments without a verdict (R54).                                 |
| `src/hold.ts`                     | New lines kept out of sight until judged (R52): posting order, 2 s, 300 lines, the chat's scroll.       |
| `src/runtime.ts`                  | Message routing, queues, settings and the pipeline built from them.                                     |
| `src/pipeline.ts`                 | Batching, model and Clef calls, bounds, stats; comment slots shared with summaries, cached summaries.   |
| `src/summary.ts`                  | Chat summary: the counted parts, the model's input lines and the merge of its reply.                    |
| `src/fastpath.ts`                 | Comment normalization, stock-reaction rules and the text cache.                                         |
| `src/feedback.ts`                 | Hidden-comment list, saved verdicts and what a streamer's channel learns from them.                     |
| `src/filters.ts`                  | Filter settings per streamer (schema, defaults, key, store) and spoiler targets per stream.             |
| `src/stream-context.ts`           | Stream context: partition → stream, owner key, prompt text and hash, the bounded stream registry.       |
| `src/protocol.ts`                 | Message schemas between content scripts, side panel and service worker.                                 |
| `wxt.config.ts`                   | WXT build and the manifest (name, permissions).                                                         |

## Tests

```console
pnpm --filter @chrome-toolbox/comment-assistant test
pnpm --filter @chrome-toolbox/comment-assistant exec playwright install chromium
pnpm --filter @chrome-toolbox/comment-assistant test:e2e
```

- `test` runs the Vitest unit tests in `test/unit/` with WXT's fake browser: the fast-path rules, the feedback store against an in-memory storage area, the filter store, the stream context, the pipeline against a fake llama.cpp client and fake timers, the chat summary (window, busy minutes, input lines and their bounds, merging the model's reply, a failing model), the service worker's routing (and that it keeps no summary timer), and (in jsdom) the site adapters, the observer (with an `IntersectionObserver` stand-in), the reader, chat session and pipeline together (`front.test.ts`: only a chat leaving the viewer stores waiting comments, and only those no other frame shows), the display, the content script session and the side panel (Testing Library; the summary's auto refresh with fake intervals and page visibility; a model name typed before the saved settings load) against the page fixtures in `test/fixtures/` (structure taken from the live sites on 2026-10-28; every name and text is made up).
- `test:e2e` builds the production extension and loads it into Playwright's Chromium with a local llama.cpp stub (`test/browser/`): connecting, an unreachable server, side panel heap that stays bounded over 30 reconnects, and the side panel naming the stream of a watch page fixture served at YouTube's URL (no request reaches YouTube), saving a filter the chat follows for that streamer and staying bounded over 20 tab switches. The chat flow runs on a made-up watch page whose live chat iframe keeps posting made-up lines (`test/browser/fixtures/live-chat.html`, `?rate=<n>` lines a second, in a list that scrolls like YouTube's and follows the newest line; the stub calls a text ending in `?` a question, has Clef score a text with `BAD` as abusive and translates as `訳:` + the text): questions highlighted, abusive lines concealed (and revealed by a click), translations in place and one platform request per document; originals and "llama.cpp に接続できません" while the stub is down, translations again once it is back; and the 5-minute summary. Only the chat in front is processed (`front.spec.ts`, R44): a chat in a background tab, collapsed (`display: none` on an ancestor), scrolled out of view or closed (its frame navigated away) gets no batch and no Clef call while its lines are stored and shown as they are, the comments waiting for the slow stub are stored when the chat closes, and back in front the lines on screen are processed, the newest three first, while stored lines off screen stay stored. A background tab is `hidden` only without Playwright's focus emulation, which keeps every page `visible`: that test uses the `realVisibility` option of the shared fixtures, which starts Chromium itself and connects with `connectOverCDP(…, { noDefaults: true })`; Playwright's emulated visibility, `Page.setWebLifecycleState` and minimizing the window did not change `visibilityState`. The soak (`soak.spec.ts`, marked by `starter.soak` in `package.json` so the runner and the gate allow for it) runs that chat at 20 lines a second for `SOAK_MINUTES` whole minutes (default 2; `SOAK_MINUTES=120 pnpm --filter @chrome-toolbox/comment-assistant test:e2e -- soak` for the long run) after a minute of warm-up (sampled each minute by the clock), and requires the chat page's heap under 30 MB and within 1.1× of its start, the side panel's objects within 1.1× of their start and its whole heap under twice its start, no long task over 50 ms in the chat frame, every comment answered (none only stored) and at most 5,000 kept. The chat page's heap is `JSHeapUsedSize` of the renderer that runs the chat: the content script together with the watch page and the fixture's own generator (about 1.9 MB of the measured 3.9 MB), so the ratio covers the chat renderer including the generator. The side panel's objects are a heap snapshot's without compiled code (`heapSnapshotParts`): while the summary re-renders every 2 minutes V8 keeps compiling the panel's hot functions (about +0.27 MB of code, levelling off after an hour), which `JSHeapUsedSize` counts and which is not a leak. The perf spec (`perf.spec.ts`, R45, about 61 s) measures what the display costs in the browser: the live chat adapter reading a line posted right after the page changed the list (under 20 µs), and at 50 lines a second, every line concealed against every line shown (main thread under 1.3×, GPU process under 1.2×) and the layouts per posted line against the same chat on a host the extension does not run on (under 1.3×). Install the browser once with the second command. No real server is needed.
