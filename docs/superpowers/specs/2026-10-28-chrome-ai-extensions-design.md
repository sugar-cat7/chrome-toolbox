## 1. 何を作るか、なぜ作るか

VTuber やストリーマーの配信を見るときの「言語の壁」と「チャットが多すぎて追えない」という問題を、ローカル LLM で解決する Chrome 拡張群を作る。主な利用者は配信を見る側の人で、英語圏や多言語の配信を日本語で楽しみたい日本語話者。配信者やモデレーター向けの道具ではない。

推論は llama.cpp を使ってローカルで行う。必要なときだけ Web API で補う。ここでいう Web API は次の 2 つに限る。

- Chrome に内蔵されている、端末上で動く API（LanguageDetector、Translator など）
- YouTube と Twitch の API

クラウドの翻訳サービスや LLM（DeepL、Gemini など）は、オプトインの形でも使わない。配信の音声やチャットの内容は、外部のサービスには送らない。

拡張は次の 3 本に分け、共有パッケージを使う（判断）。最初の依頼にあった「それぞれ独立した拡張」と、要件メモにある 3 つの領域の両方を満たす分け方にした。

| #   | パッケージ            | 領域                                                               | 優先度     |
| --- | --------------------- | ------------------------------------------------------------------ | ---------- |
| ①   | `subtitle-translator` | 動画・配信の音声を日本語字幕にする（原語の字幕も表示）             | 最初に作る |
| ②   | `comment-assistant`   | コメント・チャットの翻訳、Clef による有害判定、AI フィルター、要約 | 最初に作る |
| ③   | `page-translator`     | 一般の Web ページの翻訳と、選択範囲の翻訳                          | ①②の後     |

## 2. ゴール・非ゴール・アンチゴール

**ゴール**

- 英語をはじめ、話されている言語にかかわらず、配信をほぼ音声と同時に日本語字幕で見られる。
- 多言語のチャットを日本語で読める。不要なコメントは見えなくなり、大事なコメントは目立つ。
- 直近のチャットの流れを、要約でまとめて把握できる。
- 一般の外国語ページを、レイアウトを崩さずに日本語で読める。

ユーザーが挙げた品質の優先順位は「軽量・高速」「精度が高い」「負荷をかけない」「メモリリークを起こさない」。

**非ゴール**

- コメントを実際に削除したり、BAN やタイムアウトなどのモデレーション操作をしたりはしない。ブラウザ上の表示を切り替えるだけ。
- クラウドの LLM を常用しない。
- 初期段階では Chrome Web Store で公開しない（判断）。まず自分で未公開の拡張として読み込んで使う。公開準備は §10 の Phase 3 で行う。
- Chrome 以外のブラウザには対応しない。

**アンチゴール**（機能としては動いても、次のどれかが起きたら失敗とみなす）

- 拡張を入れると YouTube や Twitch のページが重くなる、カクつく、ファンが回る。
- 長時間視聴するとメモリが増え続ける。
- 字幕が音声から 2 秒以上遅れ続ける。
- YouTube や Twitch のサーバーに余計なリクエストを送る。
- コメントや音声の内容が、意図せず外部のサービスに送られる。

## 3. 制約

- **推論バックエンド**：llama.cpp（`llama-server`）。同じ Mac か LAN 内の端末で動かす。接続先 URL は設定で変えられる。再現できる構成の例は [docs/llama-server.md](../../llama-server.md)。
- **メモリ予算**：モデルの合計で 20GB まで。
- **字幕の遅延**：2 秒以内。
- **対象サイト**：まず YouTube と Twitch。一般のチャットにも広げられる設計にする。
- **リポジトリ**：テンプレートから生成したこのリポジトリの構成と規約に従う（AGENTS.md）。
  - アプリ同士は import しない。
  - 想定内の失敗は Result で表す（throw / catch / console を使わない）。
  - 新しいエラーコードは `tools/errors/catalog.json` に定義する。
  - 依存はカタログで正確なバージョンに固定し、公開から 24 時間以上たったものだけを使う。
- **拡張の基盤**：WXT 0.21.5 + React 19 + Tailwind 4。Vite 8（vite-plus-core）、Vitest 5、TypeScript 7 と組み合わせて動くことを検証済み（2026-10-28、scratchpad の probe）。
  - E2E テストは Playwright 1.64 で行う。Chrome for Testing を `channel: 'chromium'` の headless モードで起動し、`--load-extension` で拡張を読み込む。

## 4. 全体の構成

```
YouTube / Twitch / 一般ページ
   │  content script（DOM を読む／表示を切り替える。推論はしない）
   ▼
各拡張の service worker（ルーティング、キュー、キャッシュ、設定）
   │  ①のみ: offscreen document（タブ音声の取得、16 kHz 化と VAD、ライブの処理: ASR → 言語 → 文 → 翻訳）
   ▼
extension-core の LLM クライアント ──HTTP──▶ llama-server（ルーターモード、1 つのポート。ローカル／LAN）
                                               ├ gemma4-e4b（翻訳・分類・要約。投影器を付けると音声認識も）
                                               ├ clef-flash（有害判定）
                                               └ plamo-3-translate-2b（任意。①の字幕の翻訳だけ）
```

- **content script は軽く保つ**。推論や重い処理は、service worker か offscreen document で行う。
- **llama-server はルーターモードで 1 つのポートに置く**（判断 R21。既定は `http://127.0.0.1:18083`）。ルーターはモデルごとに子プロセスを起動し、リクエストの `model` でモデルを選ぶ。拡張はすべてのリクエストに `model` を付ける（判断 R11）。使うモデルの名前はタスクごとに設定する。
- **複数の拡張が同じ llama-server を使うときの割り振り**（判断）：サーバーを `--parallel 3` で起動し（ルーターでは、どのモデルも 3 つの枠を持つ）、リクエストの `id_slot` で枠を固定する。字幕（①）が枠 0、コメント処理が枠 1 と 2 を使う（2 つのバッチを同時に処理する。判断 R39。`--parallel 2` なら枠 1 だけを使う）。こうすると、コメントの処理が字幕の遅延を悪化させない。拡張どうしでメッセージを送り合う仕組みは作らない。ただし、字幕が枠 0 を使っている間は、コメント処理がサーバーの `/slots` で枠 0 を見て、バッチを 1 つずつにする（§7。ユーザーの決定、2026-11-06）。
  - 枠を固定したときの効果は、`bench:slots` で測った（`docs/adoption.md`）。
  - ①は、音声認識（ASR）と字幕の翻訳の両方を枠 0 に流す。音声認識は Gemma の音声入力で行い、別のサーバーは使わない（判断 R10）。2 つは同じシステム文と、配信ごとの同じ前置き（配信の文脈と用語集）を使う（判断）。枠 0 に交互に流れても、プロンプトキャッシュの先頭を共有できるようにするため。
  - 字幕の翻訳に PLaMo 3 Translate 2B を選んだとき（§6）は、訳を PLaMo の枠 0 に送る。PLaMo はルーターの別の子プロセスで、Gemma の枠を使わない。
  - Gemma の投機的デコード（MTP。`spec-type = draft-mtp`）は採用した（判断 R61）。サーバー全体の設定で、リクエストごとには切れない。コメントの生成は 1 本で約 40%、2 本で約 52% 速くなった一方、コメントの負荷の下で、字幕の翻訳だけの p95 は 1.25 秒から 1.8 秒に上がった。ASR を含めると（2026-11-06）、コメント 2 本の負荷の下では MTP の有無にかかわらず p95 が 3 秒を超え、1 本なら収まった。MTP は残し、コメントが字幕に譲る（§7）。

## 5. 共通基盤 `packages/extension-core`

ライブラリとして作る。`wxt` や `node:` は import しない。ブラウザの API は、外から渡されるアダプター経由で使う。

- **型付きメッセージ**：プロトコルとルーター。Zod mini で入力を検証し、結果は Result で返す。
- **保存**：storage のポート（インターフェース）。設定のスキーマとマイグレーションを持つ。
- **LLM クライアント**：OpenAI 互換で、llama-server の `/health`、`/v1/models`、`/props`、`/v1/chat/completions` を使う。
  - タイムアウトは AbortSignal で扱う。
  - 出力の形は JSON Schema（`response_format`）か GBNF の文法（`grammar`）で縛る。PLaMo 3 Translate には縛りを付けない（付けると出力が壊れる）。代わりに止める文字列（`stop`）を送る。
  - 指定できる項目: `model`、`id_slot`、`cache_prompt`、`chat_template_kwargs`、`stop`。
  - PLaMo 3 Translate へのリクエストは、extension-core の 1 か所（`plamo.ts`）で組み立てる。user の 1 通、`chat_template_kwargs`（訳先、原語、上限付きの文脈と用語集）、止める文字列、上限付きの `max_tokens`。枠（`id_slot`）は呼ぶ側が渡す（判断。PLaMo の枠を拡張どうしで分けるため）。①は PLaMo の枠 0 を使う。
  - user の本文に、音声の部品（`input_audio`。WAV の base64）を入れられる。①の音声認識に使う。
  - `/props?model=<name>` から、枠の数（`total_slots`）と、音声入力が使えるか（`modalities.audio`）を読む。
  - `/slots?model=<name>` から、枠ごとに処理中か（`is_processing`）を読む。②が、字幕の使う枠 0 を見るために使う（§7）。
  - 想定する失敗は Result のエラーコードで返す。①のために足すもの:
    - `audio_unsupported`: 投影器（mmproj）のないモデルに音声を送った（HTTP 400）
    - `model_refused`: HTTP 4xx/5xx。求めたリクエストだけこのコードにし、ほかは今までどおり `network_failed` にする（comment-assistant は `network_failed` で「接続できません」を出している）
- **エラーコードの定義**：`tools/errors/catalog.json`。①は、上の 2 つのほかに、タブ音声の取得の `capture_failed`（取得に失敗した）と `capture_not_invoked`（拡張が呼び出されていない）を足す。
- **キュー**：同時に処理する数（既定は 1）、待ち行列の上限、優先度を持つ。
  - 上限を超えた分は古いものから捨て、捨てた件数を数える。
- **キャッシュ**：上限付きの LRU（最近使われていないものから捨てる方式）で、正規化した原文のハッシュをキーにする。
- **後片付け**：listener、observer、タイマー、AudioContext、offscreen を登録して、まとめて確実に解放するユーティリティ。
- **サイトアダプターのインターフェース**：コメントの取得元、表示の切り替え先、動画の再生位置を抽象化する。実装は各拡張が持つ。

**設定**：各拡張がそれぞれ持つ（判断）。

- llama.cpp の接続先 URL（タスクごと）
- 使用するモデル（タスクごと）
- 翻訳先の言語（既定は日本語）
- 機能ごとの ON/OFF
- サイトごとの設定
- 同時に処理する数と、処理の頻度

LAN の IP に接続するときは `optional_host_permissions` を使い、Chrome が実行時に許可を確認する。

## 6. ① subtitle-translator（字幕翻訳）

対象は YouTube（`www.youtube.com`）の動画とライブ配信。実装の手順は [① の計画](../plans/2026-10-28-subtitle-translator.md)。

**画面**（モック A を採用）

- 映像の上に 2 段の字幕を出す。上の段は原語で小さく、下の段は日本語で大きく。
- 表示のモードは 4 つ（ユーザーの決定、2026-11-05）。既定は「原語と日本語」。
  - 日本語のみ
  - 原語と日本語（既定）
  - 原語のみ
  - オフ
- 表示は 3 か所から切り替えられる。どこで切り替えても、すべてのタブにすぐ反映する（判断）。
  - プレイヤーの右上の小さなボタン。押すたびに 日本語のみ → 原語と日本語 → 原語のみ → オフ と進む。
  - ショートカット `Alt+Shift+J`
  - サイドパネル
- 日本語の音声と日本語の字幕トラックは訳さず、そのまま日本語の段に出す。「原語と日本語」でも 1 段にする。
- 「原語のみ」のときは翻訳を呼ばない。「オフ」のときは何も処理しない。
- 上の段の英語訳はなくした（判断、2026-11-05）。英語の配信では、原語の段がそのまま英語字幕になる。最初の依頼にあった「英語字幕も表示」は、これで満たす。
- プレイヤーのボタンは、字幕の取得元と状態も示す。字幕トラックがなく、音声も始めていないときは「字幕なし・Alt+Shift+S で音声字幕」と出す。
- 操作はサイドパネルにまとめる。ポップアップは作らない（判断）。サイドパネルで操作できるもの：
  - 状態（字幕の取得元と言語、遅延、処理しきれなかった数、止まっている理由）
  - 表示のモード
  - 音声字幕の開始と停止。音声入力が使えるかどうか
  - 字幕の取得元（自動／字幕トラック／音声）
  - 話されている言語（自動、または 12 言語から 1 つ）
  - 字幕の翻訳モデル（Gemma／PLaMo 3 Translate 2B）
  - 配信者ごとの用語集
  - llama.cpp の接続先と、使うモデルの名前

**字幕をどこから得るか**

1. **字幕トラックを使う経路**：アーカイブで、YouTube の字幕トラック（自動生成を含む）がある場合。
   - プレイヤー自身が取得した timedtext の応答を読む。拡張から YouTube に字幕を取りに行かない（判断）。timedtext は PO トークンを求めるので、プレイヤーの外からは取れないと見込まれ、取れても余計なリクエストになるため。
   - 原語のトラックを選ぶ。自動生成のトラックの言語を原語とみなす。YouTube の翻訳トラックは使わない。
   - 字幕を文に区切り、再生位置の 60 秒先までを先に訳しておく。表示の遅延はほぼ 0。シークしたら、新しい位置から訳し直す。訳は再生位置の前後 10 分の分だけ持つ。
   - 先読みは content script が進め、service worker は状態を持たない翻訳係にする（判断）。service worker は、イベントのない状態が 30 秒続くと止まり、持っていた状態を失うため。
   - ライブ配信では、この経路を使わない。
2. **音声認識の経路**：ライブ配信や、字幕トラックのない動画の場合。
   - ユーザーの操作でタブ音声の取得を始める（`tabCapture.getMediaStreamId` を使い、offscreen document で `getUserMedia` する）。
   - 取得した音声は `AudioContext.destination` に戻して、タブがミュートにならないようにする。AudioContext は端末の標本化周波数のままにし、16kHz mono への変換は AudioWorklet で行う（判断）。AudioContext を 16kHz にすると、視聴者が聞く音が劣化するため。
   - VAD で発話を区切る。区切りが来なくても 1.5 秒で強制的に区切る。強制の区切りは、最後の 0.5 秒のうちいちばん静かなところで切る（判断）。2026-11-06 の計測で、1.5 秒ごとに機械的に切った音声は、音節の途中で切れて ASR が同じ語を繰り返し、失敗したため。
   - 区切った音声を、llama.cpp の音声入力（`input_audio`）で `models.asr`（既定は `gemma4-e4b`）に送る。whisper.cpp は使わない（判断 R10）。音声入力には Gemma の投影器（mmproj）が要る。
   - 原語の文字起こしをすぐ表示する。その後、文の区切りで日本語訳を表示して確定させる。
   - ライブの処理（ASR → 言語 → 文 → 翻訳）は offscreen document で動かす（判断）。service worker は止まると文の途中の状態と統計を失うが、offscreen は音声を取得している間ずっと動いているため。

- 字幕の取得元の設定は「自動」（既定）、「字幕トラック」、「音声」の 3 つ。「自動」で字幕トラックがない（ライブを含む）ときは、プレイヤーのボタンとサイドパネルで音声字幕の始め方を案内し、推論は何もしない。

**対象の言語**

- 話されている言語にかかわらず、日本語の字幕を出す（ユーザーの決定、2026-11-05）。対象を特定の言語に限らない。
- 言語の判別（判断）：
  - ASR の出力を、GBNF の文法で 1 行の `<言語コード>\t<文字起こし>` に縛り、その言語コード（ISO 639-1 の 2 文字）を使う。確からしさの値は使わない。
  - 行ごとの言語で、翻訳するかを決める。日本語の行は翻訳せず、そのまま日本語の段に出す。英語の配信に日本語が混ざる場合も、行ごとに扱える。
  - 状態の表示には、直近 20 行でいちばん多い言語を出す。
- 話されている言語は、サイドパネルで固定もできる（自動、または 12 言語）。固定したときは、文法でその言語コードだけを許す。
- 字幕トラックを使う経路では、自動生成のトラックの言語を原語とする。
- 遅延と精度を測る言語は、英語、インドネシア語、韓国語、スペイン語、中国語と、翻訳を呼ばないことを確かめる日本語（判断）。

**翻訳モデル**（ユーザーの決定、2026-11-06）

- 既定は Gemma（`models.translate`、既定は `gemma4-e4b`）。
  - ASR と同じシステム文と、配信ごとの同じ前置き（配信の文脈と用語集）を使う（§4）。
  - 訳は GBNF の文法で 1 行に縛り、長さに上限を付ける（原文の 2 倍 + 16 文字、2,000 文字まで）。コメントの翻訳と同じ考え方（判断 R20、R46）。
- サイドパネルで PLaMo 3 Translate 2B（`plamo-3-translate-2b`。Preferred Networks の翻訳専用のモデル）を選べる。任意で、利用者が自分でサーバーに入れる。
  - 2026-11-06 の実測（`docs/llama-server.md`）で、字幕の 1 文の p50 は 121ms（Gemma は 329ms）、コメントの負荷の下で 179ms（854ms）。メモリは 2.47GB。品質は英語、中国語、インドネシア語で Gemma とほぼ同じで、韓国語とスペイン語のゲームのスラングで劣った。
  - PLaMo へのリクエストは別の形式にする。1 つの user メッセージに、空でない原文 1 行だけを入れる。`chat_template_kwargs` で、訳先（`ja`）、原語（小文字の言語コード。分からないときは付けない）、直前の原文（文脈。上限付き）、用語集を渡す。`temperature` は 0、`max_tokens` は上限付きにし、止める文字列を送る。
  - JSON Schema、文法、system メッセージは送らない。JSON Schema と文法を付けると出力が壊れ、system メッセージは文脈として読まれるため。
  - 送る前に、空の行と、PLaMo の予約の記号（`<|plamo:`）を含む行を断る。言語コードは PLaMo の形（`zh-hans`、`zh-hant` など）にする。`zh-CN` のような地域付きのコードは、サーバーが断るため。
  - ルーターが PLaMo を載せていないとき、または PLaMo へのリクエストが HTTP のエラー（4xx/5xx）になったときは、その行を Gemma で訳す。サイドパネルに、Gemma に切り替えたことを出す。サーバーにつながらないときは Gemma にも送らず、その文は原語のまま出す。
  - PLaMo を選んでいる間、サイドパネルに「Built with PLaMo」と、PLaMo Community License へのリンクを出す。ライセンスの条件のため。
  - リポジトリには PLaMo の出力を入れない。テスト、fixture、文書の例は自作の文字列だけにする。
- コメントの翻訳と分類は、Gemma のまま（§7）。PLaMo はコメントの分類ができず、チャットのスラングを直訳したため。

**精度を上げる工夫**

- 直前の 3 文を文脈として一緒に渡す。
- 配信者（YouTube のチャンネル）ごとの用語集を使う。配信者の名前、ファンの呼び名、ミームなど。
  - 1 人 50 件まで、配信者は 100 人まで（判断）。
  - 訳を空にした語は、原文のまま書かせる（固有名詞を訳したり、カタカナに直したりしない）。
- 配信のタイトルとチャンネル名を、配信ごとの前置きに入れる。
- 文の途中で切れたときは、文が完結した時点で訳を差し替える。

**前面にあるときだけ処理する**（判断 R44）

- 処理するのは、次をすべて満たすときだけ。
  - タブが見えている
  - プレイヤーが画面に出ている
  - 動画が再生中
  - 広告中でない
  - ミュートでない
  - 表示がオフでない
- 一時停止とミュートの間は、新しい音声を読まない。区切りかけの発話は区切って処理し、待っている仕事は終える。
- 裏のタブ、プレイヤーが画面外、広告、表示オフの間は、新しい音声を読まない。区切りかけの発話と待っている仕事は捨て、実行中のリクエストを中断する。
- 字幕トラックの先読みも、前面で再生しているときだけ進める。

**遅延が 2 秒を超えるとき**

- 「ライブの再生を後ろにずらす」案は採用しない（判断）。`tabCapture` で取れるのは再生中の音声だけなので、再生をずらしても ASR が先に音声を受け取れるわけではなく、効果がないため。
- 追いつかない分は捨て、待ちを溜めない（判断）。
  - ASR の待ちは 2 件まで、翻訳の待ちは 2 文まで。超えたら古いものを捨てる。同じ文の翻訳の待ちは、新しい版に置き換える。
  - 発話の終わりから 1.5 秒以内に始められない ASR と、2.5 秒以内に始められない翻訳は捨てる。翻訳を捨てた文は、原語のまま出す。
  - 次に流すのは、発話の終わりがいちばん古い仕事。同じなら翻訳を先にする。
  - 捨てた数と、期限を過ぎた数をサイドパネルに出す。
- 字幕が枠 0 を使っている間、②はコメントのバッチを 1 つずつにする（ユーザーの決定、2026-11-06。§7）。2026-11-06 の計測で、コメント 2 本の負荷の下では MTP の有無にかかわらず日本語の p95 が 3 秒を超え、1 本なら収まったため。
- それでも目標に届かないときは、次の順で対処する。
  1. 区切る長さを短くする（1.5 秒 → 1.0 秒）
  2. 訳を PLaMo 3 Translate 2B にする（利用者がライセンスを受け入れて、サーバーに入れている場合）。小さい Gemma（E2B）には替えない。2026-10-28 の実測で、E4B と生成の速さが変わらなかったため。
  3. 原語だけを先に出す
- プレイヤーのバッファ（MSE）を横取りして、音声を先にデコードする方式は、壊れやすく CPU の負荷も高いため、将来の研究課題にとどめる。

**音声の取得はいつ始まり、いつ終わるか**

- 音声の取得は、ショートカット `Alt+Shift+S` か、サイドパネルの「音声で字幕を開始」でユーザーが始める（判断）。`tabCapture` の制約で、ページ内のボタンからは開始できないため。どの操作で開始できるかは、実装の最初に実機で確かめる。
- 同時に取得するのは 1 タブだけ（判断）。別のタブで始めたら、前のタブの取得を止める。
- 投影器のないサーバーでは、音声入力を使えない。拡張はこれを `/props` の `modalities.audio` で確かめ、取得を始めずに、サイドパネルで投影器の有効にし方を案内する。取得の途中で音声つきのリクエストが HTTP 400（投影器がない）になったときも、取得を止めて案内する。
- 一時停止、ミュート、裏のタブ、広告などで処理しない間も、タブ音声の取得（MediaStream）は保ち、前面に戻れば自動で再開する（ユーザーの決定、2026-11-05）。取得をやり直すにはユーザーの操作が要るため。その間は AudioWorklet を切り離し、処理はしない。
- YouTube 内の画面遷移（SPA の遷移）では、音声の取得は止めない。言語、文脈、用語集を新しい動画に切り替える。
- 音声の取得を止めるのは、次のどれかのとき：
  - タブを閉じた
  - ユーザーが停止した
  - `www.youtube.com` から離れた
  - 処理しない状態が 10 分続いた（ユーザーの決定、2026-11-05）
  - 別のタブで取得を始めた

**受け入れ基準**

- 字幕トラックの経路：字幕を表示するずれが 200ms 以内。
- 音声認識の経路（基準機、§9。①と②を同時に動かし、MTP を有効にしたプリセットで測る）：
  - 発話の終わりから原語の字幕を表示するまで、p50（中央値）で 1.0 秒以内。
  - 日本語を表示するまでは、p50 で 2.0 秒以内、p95（遅い方から 5%）で 3.0 秒以内。
- 処理が追いつかないときも、待ち行列が伸び続けない（待ちは ASR 2 件、翻訳 2 文まで）。
- 前面にない間は、llama.cpp へのリクエストが 0 件。
- YouTube への追加のリクエストは 0 件。字幕トラックは、プレイヤー自身の取得を読むだけにする。
- YouTube 内で画面遷移したとき：その動画の字幕の状態と、その動画用の observer を解放する。
- 音声の取得を止める条件（上記）を満たしたとき：MediaStream の track、AudioContext、offscreen をすべて解放する。
- 2 時間連続で再生しても、視聴ページと offscreen のヒープが §9 の予算内に収まる。
- 遅延の数値は、基準機で測る（基準機の条件は §9）。

## 7. ② comment-assistant（コメント機能）

**画面**（モック B を採用）

- チャット欄では、表示を切り替えるだけにする。切り替え方は次の 4 つ。
  - 翻訳文と原文の切り替え
  - ハイライト（質問、重要情報）
  - 伏せる（ネタバレ）。カテゴリの色の帯に「伏せたコメント（<カテゴリ>）· クリックで表示」と出し、本文、画像、バッジは見せない。行の高さは変えず、クリックで表示する（判断 R51。保存する値は `blur` のまま）。
  - 消す。行ごとチャット欄から消し、代わりのラベルも出さない。チャット欄ではクリックで戻せず、サイドパネルの「非表示」タブで理由と一緒に見返し、「問題なし」で戻す（判断 R54。保存する値は `hide` のまま）。目立たせたり伏せたりすると、かえって目を引くため。
- 操作と要約は、すべてサイドパネルに置く。タブは「要約」「フィルター」「非表示」「設定」の 4 つ（非表示は判断 R24 で追加）。
- フィルターの設定は配信者（YouTube はチャンネル、Twitch はチャンネル名）ごとに保存する。配信者が分からない間は、その配信ごとに保存する（判断 R29）。保存する記録には版（`v: 2`）を付ける。版のない記録だけを Task 5d より前の形式として読む（判断 R56）。
- 判定してから表示する（判断 R52）。チャット欄が前面にある間、サイトが足した新しい行は、判定の結果を書くまで `display:none` で出さない（サイトの要素そのものを使い、コピーは作らない）。行は投稿の順に出し、最大 2 秒で原文のまま出す（後から結果が来れば書き換える）。出す直前にチャット欄が一番下にあれば一番下に合わせ、上を読んでいる間は読んでいる行を動かさない。llama.cpp につながらない間と、フィルタータブのスイッチ「判定してから表示する（最大 2 秒）」を切った間は待たせない。判定待ちの行は、2 秒以内に判定できるものを古い順に先に処理し、ほかは新しい順に処理する（判断 R57）。間に合うかどうかは、Service Worker に届いてからの時間で判断する。目安は 2,000ms − 250ms（content script の送信間隔）− 直近 20 バッチの所要時間の 90 パーセンタイル（最近接順位）で、範囲は 0〜1,750ms。バッチを 1 つも測っていない間は 450ms とみなし、目安は 1,300ms になる（判断 R58、R59）。所要時間がばらつくと、中央値では過負荷時に新しい順より悪くなったため、90 パーセンタイルを使う。
- 拡張機能のアイコンのバッジに、そのタブの配信の非表示一覧のうち、まだ判断していない件数を出す（0 件なら出さない。判断 R54）。一覧に足したとき、判断したとき、フィードバックを消去したとき、タブの配信が変わったときに更新する。ポーリングはしない。ページの読み込みが終わったタブ（`tabs.onUpdated` の `complete`）には、トップフレームに配信を尋ねて合わせる。`tabs.onUpdated` を受けると、タブが更新されるたびに Service Worker が起きる。ただし、バッジを付けていないタブではすぐに戻る（Service Worker の再起動後に知らないタブは、Chrome がそのタブにバッジを出しているときだけ尋ねる）。

**取得方法**（判断）

- YouTube のライブチャット（iframe）、YouTube のコメント欄、Twitch のチャットはいずれも、すでにページに読み込まれている DOM を読む。
- MutationObserver は、チャットのコンテナだけを監視する。
- プラットフォームの API やチャットの WebSocket には、追加で接続しない。「負荷をかけない」という方針と、API の利用枠を考えての判断。

**処理の流れ**：1 コメントにつき推論は 1 回だけ行う。

1. コメントを取得する。
2. 言語を判定する。Chrome に内蔵されている LanguageDetector を使い、使えない環境では軽い文字種の判定で代用する。
   - 漢字（と数字、記号）だけの行は、そのチャンネルで直近に判定した 200 件のうち日本語が半数以上なら日本語とし、翻訳せずに分類だけを行う。中国語にしかない字や語を含む行は除く。数えるのは判定した言語で、この規則で日本語にした行は数えない（判断 R60）。
3. 重複を除いて、まとめて処理する単位（バッチ）を作る。最大 3 件、または 500ms ごと（判断。2026-10-28 の実測で、20 件のバッチは生成に約 25 秒かかったため 3 件に下げた）。
   - 字幕（①）が枠 0 を使っている間は、コメントの枠に同時に 1 つだけ送る（ユーザーの決定、2026-11-06）。2 つ目を始める前に、llama-server の `/slots` で枠 0 を見る（1.5 秒に 1 回まで）。処理中と最後に見てから 15 秒たてば 2 つに戻り、`/slots` が答えないサーバーでは今までどおり 2 つ（判断）。
4. Clef-flash で有害判定をする。Clef に送るのは、罵倒語の手がかりを含むコメント（LLM と並行して判定する）と、手がかりはないが LLM が攻撃的とした（その返事の後で判定し、Clef の結果が出てから表示する）コメントだけ（判断 R43）。ほかのコメントは LLM の分類がそのまま決まる。
   - 配信者、モデレーター、認証済みアカウントの投稿と、視聴者が「問題なし」にした文は、Clef に送らない（判断 R53）。
   - コピペ（同じ句の 3 回以上の繰り返し）は規則でスパムにする。ただし視聴者のコピペで罵倒語の手がかりを含むものは、バッチと一緒に Clef に送り、基準以上なら攻撃的、そうでなければスパムにする。配信者などのコピペは雑談（リンクを含めば重要情報）にする（判断 R53）。
5. 翻訳とカテゴリ分類を、LLM の 1 回の呼び出しで同時に行う。出力は 1 コメントにつき 1 行の短い形式で、GBNF の文法で縛る（判断 R20）。
   - 日本語のコメントは翻訳せず、分類だけを行う。
   - 視聴者のコメントでモデルがスパムとしたものは、リンク（`https?://` か `www.`）を含む場合だけスパムにし、それ以外は雑談にする。リンクのないものの多くは、広告への不満や助言だった。コピペの規則によるスパムは変えない（判断 R60）。
6. 結果を共通のコメントデータとして保存する。

**共通のコメントデータ**

| 項目        | 内容               |
| ----------- | ------------------ |
| 原文        |                    |
| 翻訳        |                    |
| 言語        |                    |
| カテゴリ    |                    |
| Clef の判定 |                    |
| 時刻        |                    |
| 投稿者      | 表示用の文字列のみ |

- 保持するのは、直近 30 分か最大 5,000 件のうち少ない方。古い順に入れ替える。
- フィルターと要約は、このデータを使い回す。

**カテゴリ**

- 攻撃的（Clef の判定）
- スパム・宣伝
- ネタバレ
- 質問
- 重要情報・補足
- 雑談
- ジャンルの NG（判断 R62）: 指示、他配信の話題、ゴースティング、プライバシー、センシティブ

**ジャンルごとの NG カテゴリ**（判断 R62）

- ジャンル特有の NG は、プラットフォームの規約ではなく、配信者や界隈の約束事（2026-11-05 の調査）。配信ごとに有効なカテゴリを切り替える。
- カテゴリと出力のコード:
  - 指示 `instruction`（`n`）: 頼まれていない指示・攻略の押し付け（操作、ルート、答え、何切る）。
  - 他配信の話題 `relay`（`r`）: 他の配信者の話題、伝書鳩（他の枠の実況、他の枠から来たという書き込み）。他の配信者がいる、同じゲームをやっていた、と中立に触れるだけなら雑談。配信者どうしの比較はセンシティブ（判断 R66）。
  - ゴースティング `ghosting`（`g`）: 他窓の位置情報、スナイプの予告、隠し情報の暴露（役職、手牌、待ち）。
  - プライバシー `privacy`（`v`）: 実在の人（配信者、視聴者ほか）の個人情報、前世、私生活の詮索。ゲームや作品の登場人物は対象外。
  - センシティブ `sensitive`（`e`）: 政治、宗教、センシティブな発言の誘導。判断 R66 で、次の 3 つも含める。
    - 配信者と、名前の分かる他の配信者との比較・他者下げ（褒める比較も含む）。
    - 配信者や実在の人への性的な発言・要求（体、性的に言う声、服装やカメラの要求）。
    - 実際の災害・事故・死を茶化す、不謹慎な誘導。災害を扱うゲームや作品の話は含めない。
- 有効になる条件:
  - 他配信の話題、プライバシー、センシティブは常に有効。
  - 指示は fps、story、horror、puzzle_rta、board。
  - ゴースティングは fps、board、deduction。
  - ネタバレは story、horror、puzzle_rta、watchalong、sports_viewing ではメモがなくても有効。ほかのジャンルでは、今までどおりメモがあるときだけ有効（判断 R31）。
- ジャンル: `fps`、`story`、`horror`、`puzzle_rta`、`chat`、`singing`、`watchalong`、`sports_viewing`、`board`、`deduction`、`other`（不明）。
- ジャンルの判定（判断 R63。順序は判断 R68 で変更）:
  1. 視聴者が選んだジャンル（YouTube は動画ごと。Twitch は選んだときのカテゴリのあいだだけ。判断 R69）
  2. タイトルの【】の中のジャンルの語。Twitch ではタグも同じ段で読む。
  3. 概要欄のお約束。ジャンルを決めるのは、タイトルにジャンルの語がないときだけ。見出しの形の行（【お約束】、■配信ルール、ルール：）か、この配信のことを書いた行（この配信、本配信、今日の配信、今回）の語だけを使う。条件・否定・他の配信の行（では、の時、の際、場合、苦手、注意、ません、ない、以外、他の）と、禁止や控えの行からは取らない。緩和の語は、今までどおり概要欄のお約束からも読む。
  4. ゲームカードか Twitch のカテゴリを、自作の対応表でジャンルに変換する。
  5. 決まらなければ、タイトルとゲーム名から LLM で 1 回だけ推定する（コメント用スロット、表示中の配信だけ）。Twitch の推定は、カテゴリが変わるか、表にないカテゴリのままタイトルが変わると捨て、推定し直す（判断 R69）。
  6. それでも決まらなければ `other`。
- 緩和（配信ごと）: タイトルか概要欄のお約束に「参加型」「アドバイス歓迎」「指示OK」「backseat me」があれば指示を、「ネタバレあり」「ネタバレOK」「2周目」があればネタバレを無効にする。ただし視聴者が書いたネタバレ対象のメモは、緩和より優先する。禁止や注意（ネタバレ禁止、ネタバレ注意、指示NG）、否定（「ネタバレOKじゃない」「参加型なし」「ネタバレ有無」「no spoilers allowed」「don't backseat me」）、ゲーム名の中の「ネタバレ」は緩和にしない。
- プロンプト: 固定のシステム文には、どの配信にもあるカテゴリ（攻撃的、スパム、質問、重要情報、雑談）だけを書く（判断 R25）。ジャンルの名前と、有効なカテゴリの定義（それぞれ「当てはまらないもの」を含む）は、配信ごとのユーザー側の先頭に置く。文法のコードは、有効なカテゴリだけにする。1 行 1 件の出力形式は変えない。
- 判定: 配信者、モデレーター、認証済みアカウントの投稿には付けない（判断 R38、R53）。有効でないカテゴリの判定は雑談にする。Clef は今までどおり攻撃的だけを判定する（判断 R43）。
- 評価: 自作の評価セット（ジャンルごとに 30 行以上）を実サーバーで流し、カテゴリごとの適合率と再現率、普通の雑談を NG にした割合を測る（`pnpm --filter @chrome-toolbox/bench bench:genre`、結果は adoption.md）。

**ネタバレの判定に使う文脈**（判断）

- 配信タイトルから、ゲーム名などを自動で抜き出す。
- サイドパネルで、配信ごとに「ネタバレ対象」（どのゲームの、どこまで進んだかなど）を書き足せるようにする。配信者ごとのフィルターとは別に、配信ごとに保存する（判断 R30）。
- 自由に書けるユーザー独自のルールは、Phase 1 には含めない。
- 文脈（配信タイトルとネタバレ対象）は、固定のシステムプロンプトの後ろ、配信ごとに変わるユーザー側の先頭に置く。こうすると、llama.cpp のプロンプトキャッシュが効く。タイトルの固有名詞は訳さずにそのまま使う（判断 R25 (d)）。

**流量が多いときの扱い**：処理の優先順は次の通り。

1. 画面に見えている、日本語以外のコメント
2. 新しいコメント

処理が追いつかない分は、原文のまま表示する。待ち行列から捨てた行には特別な表示をせず、その件数をサイドパネルの「設定」タブの処理の状況（「原文のまま（処理しきれず）」）に出す（判断 R53）。

**要約**

- 対象期間は直近 5 分、15 分、30 分から選ぶ。
- 内容：
  - 主な話題
  - よくある質問
  - 盛り上がり（時間ごとのコメント量の山）
  - 重要コメント
- 手動で実行するか、サイドパネルを開いている間だけ 2 分ごとに自動で更新する。
- 要約は、保存済みの翻訳とカテゴリから組み立てる。同じコメントを翻訳し直さない。

**非表示にしたコメントの見返しとフィードバック**（ユーザーの要望、2026-10-28）

- チャット欄から消したり伏せたりしたコメント（攻撃的、スパム、ネタバレ、ジャンルの NG と判定したもの）は、サイドパネルの「非表示」タブで配信ごとに見返せる。原文、訳、理由、Clef の確率、時刻を表示する。
- 一覧から「問題なし」にしたコメントは、チャット欄で表示に戻す。「正しい」と確認することもできる。
- フィードバックは端末の中（`chrome.storage.local`）だけに保存し、外部には送らない。配信者（チャンネル）ごとに、次の 4 つに使う（判断。配信者単位は判断 R29）:
  - 「問題なし」にした文を、同じチャンネルでは別の配信でも以後隠さない。
  - 直近の訂正例を、そのチャンネルの分類プロンプトに入れる。
  - Clef の判定基準を、チャンネルごとに引き上げる。
  - JSONL で書き出して、精度の評価や将来のモデル調整に使えるようにする。
- 2026-10-28 の実配信では、Clef（基準 0.5）が日本語のゲーム配信で非表示にした 9 件すべてが誤判定だった。そこで基準を 0.8 にし、「攻撃的」の既定の表示を「隠す」から「ぼかす」（判断 R51 から「伏せる」）に変えた（判断）。
- 既定の表示は判断 R54 で次のとおりにした。攻撃的とスパムは「消す」、ネタバレは「伏せる」、質問と重要情報は「ハイライト」、雑談は「表示」。ジャンルの NG（指示、他配信の話題、ゴースティング、プライバシー、センシティブ）は「消す」（判断 R62）。保存した選択は既定より優先する。

**Clef が使えない場合の代替**

- Clef には、未検証の点が 2 つある。
  - コミュニティ製の GGUF に decision head が入っていない、という報告がある。
  - llama.cpp の `/v1/systemone` エンドポイントについて、一次情報で確認できていない。
- llama.cpp で動かせない場合は、有害判定もステップ 5 の LLM 分類で代わりに行う。設定画面にはどちらの方式で判定しているかを表示する。
- Clef のリクエストが失敗しても、バッチは失敗にせず、翻訳の呼び出しも止めない。そのコメントは LLM の分類のままにし、設定画面に直近の失敗を出す。接続できない、時間切れ、そのリクエストだけの HTTP エラー（503 など）はこの扱い。HTTP 501 と 404、ルーターの「モデルが見つからない」400 なら Clef は使えないとみなし、以後は LLM の分類で判定する（判断 R53）。

**受け入れ基準**

- 秒間 10 件までのチャットなら、新着コメントの翻訳を表示するまで p50 で 2 秒以内。
  - 2026-10-28 の実測（gemma4-e4b、毎秒約 37 トークン）では、翻訳できるのは毎秒約 1 件まで。この基準は「実際に翻訳したコメント」に対して測る。新しく見えている日本語以外のコメントを優先し、追いつかない分は原文のまま表示する（判断 R13。ユーザーの確認待ち）。
- 秒間 20 件のチャットを 2 時間流し続けても：
  - メモリの増加が §9 の予算内に収まる。
  - 拡張が原因で 50ms を超える長いタスクが出ない。
- YouTube や Twitch への追加リクエストは 0 件。

## 8. ③ page-translator（Web ページ翻訳）

**画面**（モック A を採用）

- 原文を日本語に置き換える。マウスを重ねると原文を表示する。
- ポップアップでは次を操作できる：
  - 翻訳する／原文に戻す
  - 表示方法（置き換え／併記）
  - サイトごとの「常に翻訳」「翻訳しない」
- 選択した範囲は、その近くに小さな吹き出しで訳を表示する。

**処理の方針**

- テキストノードだけを差し替える。原文はメモリに保持し、すぐに元に戻せるようにする。
- 見えている範囲から順に翻訳する。IntersectionObserver を使い、画面外の部分は近づいてから翻訳する。
- 動的に増える部分は、1 つの MutationObserver で監視する。数百 ms ごとにまとめて翻訳する。
- ページを離れたら、監視とキャッシュを破棄する。
- 銀行など、翻訳しないサイトを除外リストで指定できる。

**受け入れ基準**

- 翻訳してもレイアウト、リンク、フォームが壊れない。
- 原文に戻すと、元のページと完全に同じになる。
- 長いページでも、画面外の部分を一度にまとめて推論しない。

## 9. 非機能要件（3 本共通）

**基準機**（判断。開発機を実測して決めた）

| 項目               | 内容                                                         |
| ------------------ | ------------------------------------------------------------ |
| マシン             | Apple M4 Max、メモリ 36GB                                    |
| llama-server       | Chrome と同じ Mac で動かす（LAN の端末より条件が厳しいため） |
| 同時に動かすもの   | ①と②（同じタブで配信とチャットを見ている状態）               |
| モデルに使うメモリ | 20GB まで。残り約 16GB を OS と Chrome が使う                |

LAN 上の端末で動かす場合は参考値として測る。

**メモリ予算**（判断）

- content script の JS ヒープは 30MB 以内。①の offscreen document も 30MB 以内。
- 2 時間の負荷試験で、ヒープの増加が開始時の 10% 以内。測るのは、ヒープのスナップショットのうちデータの部分（コンパイル済みのコードとネイティブを除く）。ヒープ全体は開始時の 2 倍未満（判断 R47）。コンパイル済みのコードはコードの大きさで頭打ちになり、リークではないため。①では視聴ページと offscreen のそれぞれで測る。
- キャッシュと待ち行列は、すべて上限付きにする。

**CPU**

- 拡張が原因で、メインスレッドに 50ms を超える長いタスクを出さない。①の offscreen document でも出さない。
- 定期的な問い合わせ（ポーリング）はしない。イベントを受けて動く方式にする。

**ライフサイクル**

- タブを閉じる、移動する、YouTube の SPA で画面が遷移する、拡張が更新される、のいずれでも後片付けを確実に行う。
- offscreen は、音声を取得している間だけ存在させる。

**プライバシー**

- 推論の送り先は、設定した llama.cpp だけにする。
- コメントや音声は、ディスクに長期保存しない。保存するのは、用語集と設定、それに視聴者が見返して判断したコメント（原文、訳、カテゴリ、Clef の確率、判断、時刻。新しい 1,000 件を、消去するまで `chrome.storage.local` に置く。判断 R27）だけ。
- ①は、音声をディスクにもストレージにも書かない。PCM は上限付きのバッファにだけ置く。文字起こしの履歴も残さず、持つのは表示中の行と直前の 3 文だけ。

**計測**

- Phase 1 では、遅延と、待ち行列から捨てた件数をメモリ上で集計し、サイドパネルとポップアップに表示するだけにする。
  - subtitle-translator は、サイドパネルの「状態」に、原語 p50、日本語 p50 / p95（直近 200 件）、処理しきれなかった数（捨てた数と期限切れの数）、無音の数を出す。開いたとき、タブが変わったとき、「更新」を押したときだけ取得し、ポーリングはしない。
  - comment-assistant は、サイドパネルの「設定」タブに配信ごとの処理の状況を出す（判断 R53）。「処理待ち」、「原文のまま（処理しきれず）」（待ち時間切れと、待ち行列から捨てた件数）、「画面外で未処理」（保存だけした件数）、「保存できず」（保存だけするはずのコメントのうち、空けられるチャンネルがなく保存しなかった件数。1 件以上のときだけ出す。判断 R55）、「応答の中央値」（モデルの待ち行列に入ったコメントの、届いてから最初の表示までの中央値。規則やキャッシュですぐ答えたコメントは含めない。直近 200 件を、パイプラインで計る。判断 R55）。タブを開いたときと「更新」を押したときだけ取得し、ポーリングはしない。
- リポジトリの observability パッケージに出力する対応は、Phase 3 で行う（判断）。

## 11. テスト戦略

- **ユニット**：Vitest と WXT の fake browser を使い、テーブル形式でテストを書く。
  - 対象：キュー、キャッシュ、プロトコル、パーサー、DOM アダプター（DOM のスナップショット fixture を使う）。
- **E2E**：Playwright で、実際の Chrome for Testing に拡張を読み込んで動かす。
  - llama.cpp の代わりに、127.0.0.1 で動くスタブサーバーを使う。①のために、音声入力（`input_audio`）と PLaMo の形式のリクエストにも答える。スタブが返す文字起こしと訳は、自作の文字列にする（PLaMo の出力は使わない）。
  - YouTube や Twitch の代わりに、ローカルで配信する fixture ページを使う。実サイトにはアクセスしない。
- **負荷試験（soak）**：E2E の中で、チャットの流量や字幕の流れを長時間流し続ける。
  - CDP の `Performance.getMetrics` でヒープを測る。
  - CI では短縮版を回し、2 時間版は手動または夜間に回す。
- **実機での検証**：本物の llama.cpp とモデルで、遅延と精度を測る。品質ゲートとは分けて手順化する。

## 12. ユーザーが決めたこと

- ローカル LLM を基本とし、必要なときだけ Web API で補う。クラウドの翻訳サービスや LLM は使わない。
- llama.cpp は、同じ Mac か LAN 内の端末で動かす。モデルのメモリは 20GB まで。
- 字幕の遅延は 2 秒以内。
- 字幕は英語以外の配信（インドネシア語、韓国語など）も対象にし、言語は自動で判別する。
- 軽量・高速・高精度。負荷をかけず、メモリリークに注意する。
- 画面：
  - 字幕は、映像の上に 2 段で表示する。
  - コメントは、操作をサイドパネルに集約し、チャット欄では表示の切り替えだけを行う。
  - ページ翻訳は、原文を日本語に置き換える。
- 優先度：①と②が先、③はその後。
- Clef：Cloudflare の意思決定モデルで、llama.cpp から使う。
- 字幕は、話されている言語にかかわらず日本語で出し、表示を「日本語のみ／原語と日本語／原語のみ／オフ」から切り替えられるようにする。既定は「原語と日本語」（2026-11-05）。
- 一時停止、ミュート、裏のタブ、広告の間も音声の取得を保ち、前面に戻れば自動で再開する。処理しない状態が 10 分続いたら取得をやめる（2026-11-05）。
- 字幕の翻訳に PLaMo 3 Translate 2B を任意で選べるようにする。既定は Gemma。PLaMo が使えないときは、その行を Gemma で訳し、サイドパネルで知らせる。PLaMo を選んでいる間は「Built with PLaMo」とライセンスへのリンクを出す（2026-11-06）。
- 字幕中はコメントが譲る。Gemma の MTP は残し、字幕が枠 0 を使っている間、コメントのバッチは 2 つではなく 1 つずつにする（2026-11-06）。

## 13. 設計者の判断（要確認）

- 拡張を 3 本に分け、`extension-core` を共有する。
- モデルの割り振りは、llama-server の枠（`id_slot`）を固定する方式にする。
- コメントは DOM から取得し、API には接続しない。
- 初期段階はストアに公開しない。
- 字幕の上の段は原語にし、英語訳の段は作らない。
- 言語の判別は、ASR の出力行の言語コードで行い、確からしさの値は使わない。状態の表示には直近 20 行の多数を出す。
- 字幕の遅延を測る対象言語は、英語、インドネシア語、韓国語、スペイン語、中国語の 5 つと、翻訳を呼ばないことを確かめる日本語にする。
- 音声認識は Gemma の音声入力で行い、ASR と字幕の翻訳は枠 0 で、システム文と配信ごとの前置きを共有する。
- ライブの処理は offscreen document に置き、字幕トラックの先読みは content script が進める。
- 字幕で追いつかない分は捨てる（待ちは ASR 2 件・翻訳 2 文まで、開始の期限は発話の終わりから 1.5 秒・2.5 秒）。
- 設定は各拡張がそれぞれ持つ。
- §9 の数値予算と基準機（M4 Max 36GB、llama-server は同じ Mac）。
- 「ライブの再生を後ろにずらす」案は採用しない。音声の取得は同時に 1 タブだけにし、YouTube 内の画面遷移では止めない。
- ネタバレの文脈は、タイトルからの自動抽出と、配信ごとの手入力で与える。自由に書ける独自ルールは後回しにする。
- 評価用データは、実際の配信から取ったものをローカルだけに置く。訳の質は、LLM による評価と、ユーザーによる 20 文の抜き取り確認で判断する。

## 15. リスクと未検証の項目

- **Clef の GGUF と llama.cpp 対応**：エンドポイント `POST /v1/systemone` は、llama.cpp の PR [#29818](https://github.com/ggml-org/llama.cpp/pull/29818)（`a4cb4c61fd9d9c2066c7c1747821d3d65b8943bd`）と、Clef 対応の [#29831](https://github.com/ggml-org/llama.cpp/pull/29831)（`99b95488cac0f00ce3f05af113a8c1e287753f87`）で、一次情報から確認できた（詳細は `docs/adoption.md`）。ただし、判定の精度は未測定である。Apple Metal では b11475 以降が必要で、Clef サーバーは `-ub 2048` で起動する。使えない場合や精度が足りない場合は、§7 の代替方式で対応する。
- **2 秒の遅延目標**：ASR と翻訳を合わせた値は、2026-11-06 に合成音声で測った（`docs/adoption.md`）。コメント 1 本の負荷なら目標内（MTP ありで p95 1.86〜2.30 秒）、2 本では外れたので、コメントが譲る（§7）。実際の配信での値は、①の計画の最後に測る。達成できない場合は、§6 の「遅延が 2 秒を超えるとき」の順で対処する。
- **MTP と字幕の遅延**：Gemma の投機的デコード（MTP）はサーバー全体の設定で、リクエストごとには切れない。ASR を含めると、コメント 2 本の負荷の下で、MTP の有無にかかわらず 3 秒を超えた。ユーザーが決めた（§12）: MTP は残し、字幕中はコメントが 1 つずつにする。
- **投影器（mmproj）**：音声認識には Gemma の投影器が要る。BF16 にした。BF16 のファイルは 945MiB がプロセスのメモリに読み込まれ、音声認識を使うと Gemma のプライベートメモリは約 1.2〜1.4GB 増える。Q8_0 は精度が同じでメモリが 0.4〜0.5GB 少ないが、4〜17% 遅かった（2026-11-06）。
- **YouTube の字幕トラック**：timedtext は PO トークンを求めるので、プレイヤー自身の取得を読むだけにする。プレイヤーの作りが変わると読めなくなる。実サイトでの形は、①の計画の最初に確かめる。
- **`tabCapture` の制約**：ユーザーの操作がないと開始できない。どの操作のあとなら開始できるか（ショートカット、サイドパネルのボタン）と、自動テストでどこまで扱えるかは、①の計画の中で実機で確かめる。
- **PLaMo 3 Translate**：PLaMo Community License で配られている。個人と非商用は登録なしで無料、商用は事前の登録と売上の条件があり、訳を他人に渡すときは「Built with PLaMo」と PLaMo の出力であることの表示が要る。リポジトリには PLaMo の出力を入れない。llama.cpp はまだ PLaMo の YaRN の設定（`truncate=false`）を扱わない（[#30337](https://github.com/ggml-org/llama.cpp/pull/30337)）。入ったら測り直す。
- **Local Network Access**：Chrome 142 以降、ローカルネットワークへのアクセスに確認が出るようになった。ホストの権限を持つ拡張は対象外という非公式な回答はあるが、公式には確認できていない。
- **DOM の仕様変更**：YouTube や Twitch の DOM 変更で動かなくなる可能性がある。アダプターを分離し、fixture を使ったテストで、壊れたときにすぐ気づけるようにする。
